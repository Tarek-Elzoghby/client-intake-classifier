I started my first n8n with AI integration project: an AI-powered client intake classifier for an automation agency. The idea is simple on the surface — a client fills out a form, an LLM reads their project description, and the system routes it into a category with a tailored confirmation email, an internal notification, and a logged row in Google Sheets. But getting there properly took more thought than I expected.

I planned it in three phases: first the form and the AI classification, then the routing logic with a fallback for uncertain cases, then the actual outputs — emails and sheet logging, each varying by category. Working this way meant I could verify each layer actually worked before stacking the next one on top.

I set up the Form Trigger first and pinned a real test submission — a project description that's genuinely mixed, part simple notification, part AI classification work. That turned out to be a great edge case to keep in the back of my mind.

Then I hit my first real design decision: how do I get consistent, structured output from an LLM instead of loose text I'd have to parse? I learned about structured output parsers and JSON schemas — a way of forcing the model to always return data in an exact shape, so downstream nodes could reliably branch on it. I built out a Basic LLM Chain wired to a Gemini Chat Model and a Structured Output Parser.

While defining my three categories, I realized a plain three-way split wasn't enough. What happens if someone submits something that doesn't even fit — or fits more than one bucket? I found myself needing to separate two very different failure cases: a real project that's genuinely ambiguous between categories, versus input that isn't a project description at all. Treating those the same would've been misleading — an "ambiguous" label implies a real lead worth reviewing, and junk input isn't that. So I landed on five categories total: three real ones, plus ambiguous and invalid.

I also had to properly understand JSON schemas from scratch — properties, type, enum, and required aren't nested the way I first assumed. Once it clicked, I added a reasoning field alongside category, since a bare label with no explanation wouldn't be useful for whoever reads the internal notification later.

Now I moved into actually writing the classification prompt — the piece that controls the model's judgment, not just the shape of its answer. I built it in four pieces: a role/framing sentence establishing what the assistant is and its one job; definitions for all five categories, including a real revision on ambiguous and invalid after I realized my first draft of invalid ("missing information") overlapped with what ambiguous should cover — I worked out the actual test was whether a human could still make a call with what's there (ambiguous) versus whether there's nothing usable to route at all (invalid); an explicit tie-breaking instruction telling the model to choose ambiguous or invalid instead of guessing when torn; and finally assembling all four pieces with the input variable.

I hit my first real wall: the classification node kept failing with "Failed to parse agent steps." I dug into it properly instead of guessing — checked the raw model output first, and found Gemini's answer was actually fine, it was my Structured Output Parser that still had the old three-category schema; I'd updated the prompt to five categories and forgot the parser had its own separate schema field. Fixed that, and it still failed with the same error. That sent me digging deeper, and I found out this one wasn't on me at all — it's a documented bug in n8n itself, where newer versions of the Basic LLM Chain node route output through logic meant for AI Agents, which breaks structured parsing even when the model's response is completely correct. Updated n8n, and it resolved cleanly.

Then I ran into a data flow issue: the LLM Chain node's output was replacing my original form data entirely, so Name, Email, and description were gone by the time classification finished. I chose to merge everything into one clean flat object right after classification — rather than having every later node reach backward to different earlier nodes for different fields — so there's one clear point downstream where the record is complete and everything after just consumes it.

Before moving on, I went back and renamed every Phase 1 node — role first, specific to this workflow, so nothing on the canvas would need opening just to know what it does.

Before starting Phase 2, I also stopped to question whether a Switch node with a fallback was even the right tool, versus letting an AI Agent handle the ambiguous/invalid routing and email decisions itself. I reasoned through it and landed on sticking with explicit branching: I already know the full set of possible outcomes ahead of time, I just don't know which one applies to a given input — that's a lookup, not a decision that benefits from being handed to a model. An agent would also add a second layer of unpredictability stacked on top of classification, and it turned out to rely on the exact same fragile "agent steps" parsing machinery I'd just fought through a real bug in.

I moved into Phase 2 — the routing logic. Before building anything, I questioned whether we even needed a Switch node's fallback output, since I'd reasoned that the Structured Output Parser would reject anything outside my five valid categories before it ever reached a Switch. That held up — but it led to the real question I'd missed: what happens if classification fails entirely, not just returns something unexpected? I realized a hard failure — network issue, rate limit, a broken response — would crash the whole execution by default, which directly violates my own "not a broken workflow" requirement.

I decided a failed classification should route to the same human-review path as ambiguous, but stay distinguishable in the data as its own case — system_error — since "the model couldn't decide" and "the model never got to look" are genuinely different signals if I'm reviewing this later. Before falling back, I added retry logic: 3 attempts, 5 seconds apart (n8n's actual max, lower than I first wanted). I tested it by killing my own network mid-run and watched the retries fire in the execution log before it gracefully fell through to the error-handling path with the client's original data intact.

Then I built the Switch itself: six rules, one per category, with ambiguous and system_error kept as separate rules but wired to converge on the same downstream node — matching stays granular, routing consolidates where it makes sense. Once it was working, I renamed the Switch node and all six rules using the same convention as Phase 1 — the rules for ambiguous, system_error, and invalid also got a short suffix naming the consequence, not just the category, so I'd know at a glance what each one meant without opening it.

Moving into Phase 3, I initially planned to handle each category the same way I structured the first two phases — Sheets first, then emails, one branch at a time. But once I thought it through, I caught a real conflict: Sheets logging is identical logic across all five outcomes, just different data. If I put it first inside each branch, I'd either duplicate the same Sheets node five times, or converge everything after Sheets and then have to branch all over again just to send category-specific emails. Neither made sense.

So I flipped the order: build each branch's confirmation email and internal notification first, since that's the part that's actually different per category — then let all five paths converge into one single shared Sheets node at the end, the same way I already handled convergence back when I built the retry/error-handling path. Sheets doesn't care which branch a row came from, it just needs the data, so there's no reason to duplicate it.

I started with the ambiguous/system_error branch first, since it forces both categories through shared logic. Working through it, I realized the internal notification and client email needed different treatment. The internal notification could stay shared — my team needs the same information either way, they just need to clearly tell "needs manual categorizing" apart from "needs a systems check." The client email, though, genuinely needed to split: a system_error submission hasn't actually been classified at all, so a generic "we've received your message" doesn't fit it — it needs to ask for more information instead, the way I'd treat an invalid submission. I decided to split just the client-email step into its own branch rather than cramming both messages into one conditional template, since content that different deserves to stay as plain, separately readable templates instead of logic buried in text.

I wrote the internal notification myself — a subject line with an inline conditional flagging urgency and which case it is, the category and raw reasoning field, full client contact info and original message, and a closing line spelling out what action is actually needed depending on the case.

Then I hit my first OAuth setup, first time doing this myself. Two real blockers: an unauthorized redirect URI in Google Cloud Console, which I traced to needing to register my n8n callback URL; and an unverified-app block, fixed by adding myself as a test user. After that, credentials worked but the Gmail node itself still failed — turns out enabling OAuth and enabling the actual Gmail API are two separate steps in Google Cloud Console. Enabled it directly from the link in the error message, and it ran clean.

Starting Phase 3, I picked the ambiguous/system_error branch first, since building for two categories at once would force me to get the shared parts genuinely right, not just working for one case.

I separated the internal notification from the client emails early, because they're for different audiences with different needs. My team needs to clearly tell "needs manual categorizing" apart from "needs a systems check" — so the internal notification stayed one shared node, built around the category, the raw reasoning field, full client contact info, and a closing line spelling out what action each case actually needs. The client side was different: a system_error submission was never actually classified, so a generic "we've received your message" doesn't fit it the way it fits ambiguous. I split just the client-email step into its own branch, using an IF node checking whether the category equals system_error, rather than folding both messages into one conditional template — the content was different enough that keeping them as two plain, readable emails made more sense than logic buried in text.

My first drafts of the two client emails ended up almost identical, which defeated the point of splitting them. I pushed back on that when it was flagged, since I realized the hedge in the system_error draft — "we may need a bit more detail" — wasn't weak writing, it was actually accurate: a system_error submission's real outcome is still unknown at that point, it could turn out valid, ambiguous, or genuinely invalid once someone manually looks at it, and only the invalid case needs more info from the client. Comparing both drafts side by side afterward confirmed they now differ in real information content, not just tone.

I also hit a data-flow issue before wiring the IF node: sending through Gmail replaces the item's data with Gmail's own send-confirmation output, same problem as the LLM Chain node overwriting data back in Phase 1. Rather than have the IF node and both client emails each reach back to whichever of two possible earlier nodes actually produced the data, I added a Set node right after the internal notification to rebuild one clean object once, so everything downstream just reads from it directly.

Closed out the branch by renaming everything — the IF node and all three email nodes — following the same role-first convention as Phase 1 and Phase 2's Switch.

I moved into the simple_automation branch next — simpler on paper than the last one, since it's a single category with no dual-audience split to untangle.

I wrote the internal notification first: client info, category, and the original description, short and functional since there's only one reader and no ambiguity to explain. Then the client-facing confirmation email, where the real constraint was the spec's requirement to "reference their category naturally" — no internal labels leaking into client language. I translated my own internal definition of the category into plain terms a client would actually want to read, and added honest turnaround-time framing, since fast delivery is something I can genuinely promise for this category specifically, unlike the hedged tone the ambiguous/system_error emails needed.

Same data-flow issue showed up again after the client email — Gmail's send action overwrites the item with its own output, same as before — so I added another Set node after it to rebuild the flat object before it reaches the shared Sheets node later. Held off on renaming any of the three nodes for now, planning to do a renaming pass across all branches at once instead of one at a time.

Testing it against a real description — "when a client submits the form on my website, notify me and log it to a sheet" — surfaced an actual bug: it got classified as ambiguous instead of simple_automation, because my original category definition only allowed exactly one action off a trigger. That sent me back into the prompt itself for a real rewrite, not a patch.

I redefined the three real categories around what actually distinguishes them — conditional logic, real data transformation, and AI reasoning — instead of counting actions. That surfaced a deeper structural problem: my evaluation was sequential, forcing the model to commit to a single category before it ever got the chance to check whether another one also fit, so genuine overlaps were getting silently resolved by the model's best guess instead of correctly reaching ambiguous. I confirmed this with a real test case — "route incoming leads smartly based on their details" — and watched the reasoning field admit it saw two valid readings and picked one anyway. I rebuilt the evaluation method around independently checking all three categories and counting how many plausibly fit, rather than funneling through one decision path.

That fix exposed a second issue: the schema listed category before reasoning, meaning the model was structurally forced to output its answer before ever writing the reasoning meant to inform it. Reordering the schema fields so reasoning comes first fixed that.

Testing again, the new AI-signal wording overcorrected — "automatically" got flagged as a possible AI signal, when it really just means "not manual" and applies to nearly every automation request regardless of category. I tightened the definitions to require a specific grounding phrase or word for each category, and explicitly excluded words like "automatically" from counting as AI signals.

Finally, I cleaned up a leftover [TIE-BREAKING] section that duplicated the new evaluation method's logic, just less precisely, and reran both the original bug case and the genuine ambiguous case to confirm the prompt now handles both correctly.

Before moving to the next branch, I went back and did a full renaming pass — nine nodes across the two completed branches, all following the same role-first convention from Phase 1: the ambiguous/system_error branch's internal notification, its rebuild-after-notification Set node, the IF node, both client emails, and the Switch node itself, plus the simple_automation branch's internal notification, client email, and rebuild-after-client-email Set node. Since I now have multiple "rebuild the record after Gmail overwrote it" nodes across different branches, I added branch-specific suffixes so they're distinguishable on the canvas instead of all sharing one generic name.

Moved into the ai_workflow branch next. The internal notification followed the same mechanical shape as every branch before it — no new design needed there, just client info, category, and the description.

The client email needed more thought, though. Rather than reusing the simple_automation template with different wording, I worked out what's actually different about this category: it's not just "takes longer," it's that getting the AI's judgment right is the work, which is a real reason a client deserves to hear, not just a timeline to accept. I built the process around that — a scoping step that explicitly asks for real examples, since you genuinely can't judge whether an AI's output is good without seeing what "good" looks like for that client's case, something a simple automation would never need to ask for. Closed with an honest reframe: the extra time buys handling real-world cases, not just the happy path, instead of just apologizing for a longer timeline.

Same Gmail-overwrite issue as every prior branch — added a Set node after the client email to rebuild the flat record before it reaches the shared Sheets node.

For testing, I went further than a simple check this time — I wrote a description that stacked multiple category signals into one input on purpose: real conditional branching ("if it's not feedback, stop"), multi-system orchestration (Gmail, a Data Table, Slack), and clear AI reasoning (sentiment extraction, summarization, drafting a reply) all at once. That's a harder test than checking a single AI-signal word in isolation — it checks whether the prompt correctly prioritizes AI over custom_integration when a description legitimately qualifies for both. The reasoning field showed the model explicitly weighing the branching/orchestration signals against the AI signals and correctly applying my own exclusion rule — that custom_integration only applies when logic is driven by fixed rules, not AI reasoning — to land on ai_workflow. Closed the branch out by renaming its three nodes following the same convention as before.

Closed out custom_integration by writing the client email around a different honest pitch than the other two — this one isn't about speed or AI judgment, it's about correctness: making sure every path through the branching logic holds up, not just the common case. Tested it against a real branching scenario (budget-based lead routing across HubSpot, Slack, and Mailchimp) with deliberately no AI language in the description, to check the opposite failure mode from the ai_workflow test — that genuine complexity alone doesn't get miscategorized as ai_workflow just because it's multi-system. The reasoning correctly ruled out both other categories using my own exclusion language. Renamed all three nodes and moved to the last branch.

Before writing anything for invalid, I stopped to think through whether it needed the same kind of split I'd already done once for ambiguous/system_error. Looking at my own invalid definition — gibberish, out-of-scope content, or missing critical information — I realized those aren't one situation, they're at least two: a genuine but underspecified project attempt, versus something that isn't really a lead at all. Those need different client emails, the same way ambiguous and system_error did.

The problem was that my classifier only ever output a single invalid category with no way to tell which sub-case triggered it — routing on the reasoning text itself would mean parsing prose for keywords, which I recognized as fragile for the same reason structured output existed in the first place. I considered building this as a real conditional schema — Gemini only fits it under one category if the other applies — but researched it and found that while Gemini's API does now support conditional schema keywords like anyOf, I'm going through n8n's Structured Output Parser, which builds its own internal schema translation layer — the same layer that silently added an unexplained "output" wrapper to my schema earlier without either of us writing it. Given that unknown, I chose the same fix as the ambiguous/system_error branch: a flat, always-present boolean field, has_partial_intent, rather than a genuinely conditional schema — proven and consistent over theoretically cleaner but unverified in this specific tool.

I added the field to both the schema and the prompt — under the invalid definition itself, since it's a refinement of that category specifically, not a new independent decision, plus a small addition to the reasoning format so the model explains which sub-case applies rather than just filling the field mechanically.

Tested it against three real cases: a genuine but vague project request ("help automating my workflow") correctly returned true; an out-of-scope but perfectly coherent request ("fix my car") correctly returned false, which turned out to be a sharper test than plain gibberish since it proved the model wasn't just treating "makes grammatical sense" as partial intent — it correctly reasoned about domain fit specifically; and actual gibberish ("I love football") also correctly returned false, with the reasoning explicitly contrasting itself against the vague-but-real example to justify why.

While wiring the final Sheets node, I flagged something in my own wiring: the ambiguous/system_error branch was feeding Sheets from two different points off the same rebuild node — one path through the client emails, one straight to Sheets. It turned out not to be a bug — since the email path never reconnected to Sheets, there was no duplicate logging — but it revealed I'd solved the exact same "Gmail overwrites the item" problem two different ways across the workflow: rebuilding after the email everywhere else, versus branching before the email in this one branch, since Sheets never actually needed anything the email step produced.

That comparison led to a bigger redesign. I realized that since every branch converges on one Sheets node regardless of category, there was no real reason for Sheets to depend on any client email succeeding at all — so I moved the Sheets connection back to the two points right after classification and error-handling, before any branching or emails happen. That decoupled logging completely from whether any Gmail send works, which matters given a real send could fail for its own reasons unrelated to classification. It also meant has_partial_intent only needed adding in two places instead of four, and let me remove every end-of-branch rebuild node that existed purely to feed the old Sheets wiring — keeping only the ones that genuinely fed a client email's own data.

Before touching anything, I confirmed with myself which nodes were safe to remove versus which still fed live email content, since deleting the wrong one would've silently broken a client-facing email, not just Sheets.

I retested every branch individually after the rewiring, checking real inboxes rather than trusting node output alone. That method caught a real bug in the ai_workflow branch — the internal notification and client email had their destinations swapped, sending the internal-only message to the client and vice versa. I confirmed the same mistake hadn't slipped into the already-tested simple_automation branch, since I'd used the same inbox-checking method there too.

Testing ambiguous specifically exposed a flaw in my own first test case — a deliberately vague description landed on invalid instead, and walking through the reasoning showed the classifier was actually right: vague language alone doesn't ground a real signal for any category, which is a genuinely different failure than two categories both being concretely, textually supported at once. Built a sharper test case with explicit signals for both ai_workflow and custom_integration in the same description, and that correctly resolved to ambiguous.

For system_error, I needed a way to fail classification specifically without losing my whole network connection, since I needed live email delivery to verify the output. I temporarily broke the Gemini node's credentials instead, which forced the same retry-then-fallback path without touching anything else, and reverted the key afterward.

Closed out by testing the invalid/false path deliberately — confirming a genuinely out-of-scope input produces no emails at all and still logs to Sheets, which was the one silent case worth proving on purpose. Named the final Sheets node, the only node in the whole workflow that had gone unnamed through all the redesign.

Walked the finished build back against my original project spec line by line: every stated requirement met, and the classification model itself ended up going well past the original three-category ask — five real categories, a sub-distinction inside invalid, retry logic, and graceful fallback that never crashes the workflow — all individually tested, including the actual boundaries between categories, not just the categories in isolation.
